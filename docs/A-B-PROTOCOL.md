# A/B 对照实验协议 · 官方 Agent Teams vs Token 2b IQ（严格流水线）

> 目的：用可复现的数据回答一句话——**「用 token 换 IQ」到底换来了什么？值不值？**
> 本协议不靠感觉，靠同任务对照 + 客观指标。插件只是「流程脚手架」，价值必须由数据证明，证明不了就简化或下线。

---

## 1. 假设（要被证伪的）

- **H1（成功率）**：Token 2b IQ 严格流水线（spec→实现→互审→验证硬门禁）相比「官方 Agent Teams 裸跑」，**任务一次验收通过率更高**。
- **H2（返工）**：严格流水线的 **评审 FAIL→返工循环次数更少**（问题在交付前被拦住）。
- **H3（成本）**：代价是**总 token 更高**；衡量的是「每多花 1× token，换来多少通过率/返工改善」是否划算。

决策原则：**通过率 +≥15pp，或返工 −≥40%，且总 token ≤ 2×** → 值得默认开 strict；否则默认 off，仅在「高风险/多文件」任务上手动开。

---

## 2. 实验单元与分组

- 任务池：≥ **12 个** 真实开发任务，按难度分层（小=单文件、中=多文件、大=架构/迁移），每层 ≥4 个。
- 每个任务跑 **两个臂（arm）**：
  - **对照组 C**：官方 Agent Teams 裸跑（不启插件，或插件 `pipelineGate=off` 且不起团队）。
  - **实验组 T**：插件 `pipelineGate=strict` + `forceTeam=on` + `independentReview=on` + `requireDifferentVendor=on`，`candidates=1`（高风险大任务可 `candidates=3`）。
- **顺序配平**：每个任务随机决定先 C 还是先 T，抵消学习/缓存效应。
- **隔离**：一个任务一个**全新会话**，同一模型、同一仓库、同一初始 commit；每轮开始前 `git reset --hard <base>` 并清缓存依赖。

---

## 3. 指标（逐任务记录）

| 指标 | 定义 | 采集方式 |
|---|---|---|
| 一次通过率 | 交付即通过**隐藏验收测试**（不告诉 worker）的比例 | 验收测试套件 |
| 验收通过轮数 | 到通过为止的返工次数 | 人工/CI |
| 真实 token | 该任务全程 input+output（含缓存读） | 插件 `run.real.total`；对照组用宿主 tokenMeter / `/token2biq/state` 的 `liveUsage` 前后差值 |
| 返工循环 | review FAIL 次数 | 插件 `run.tasks` 中 FAIL 计数；对照组人工记 |
| 墙钟时延 | 任务开始到交付 | 时间戳 |
| 人工介入 | 人手动纠正次数 | 日志 |

> ⚠ 真实 token 归属：插件把「运行活跃期的全进程用量」计入当前 run，属**近似**。**务必一次只跑一个任务、单会话**，否则会混入其他对话用量。对照组同理用「单会话 liveUsage 前后差」估算。

---

## 4. 运行步骤（每次一个任务）

1. 起全新会话，切到 base commit，`pipelineGate=off`（组 C）或 `strict`（组 T）。
2. 组 T：模型调 `token2biq action=start {mode:Auto|S2|S3, candidates:1}`；按 roster 监督执行；每阶段 `record`，`finish`。
3. 组 C：直接让官方 Agent Teams 完成同一任务（同验收标准）。
4. 记录第 3 节指标 → 写入下表。
5. 清理会话，下个任务反序。

## 6. 分析

- 按难度分层看均值；报告 **T vs C 的差值（pp）与 token 倍数**。
- 重点关注「多文件/架构」大任务——小任务若 T 没有明显收益，就**不要**在小任务上开 strict（白烧 token）。
- 结论落回 H1/H2/H3 与第 1 节决策规则：**默认开 / 仅高风险开 / 关闭**。

## 7. 前置条件与已知坑

- **必须完整重启 DSH** 才能加载本插件的宿主侧新代码（`index.js/service.js/orchestrator.js`）。
- 一次只跑一个任务，避免 token 归属污染。
- 隐藏验收测试是关键：没有客观测试当「裁判」，A/B 退化成「看谁写得好看」，无意义。
- 若某臂 spawn 失败/任务板异常，记为无效样本，不外推。
