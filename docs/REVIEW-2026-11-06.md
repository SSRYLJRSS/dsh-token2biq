## 一、它到底在做什么（先厘清边界）

Token 2b IQ 是 DSH（Cordis）的 bundle 插件，定位是**多代理编排的「策略层 + 账本 + 看板」**，本身**不跑模型、不建 agent 运行时**：

- `lib/orchestrator.js`：4 档位 PLANS、`classify`/`generatePlan`/`buildTeamPlaybook`（把档位翻译成「官方 Agent Teams」执行手册）。
- `lib/service.js`：`start/record/finish/state/mode/settings` 等业务；`noteUsage` 采集宿主 `llm/stream` 的用量。
- `lib/run-store.js`：JSON 原子写持久化（run/stage/task/review/verdict/ledger 8 实体）。
- `lib/receipts.js`：各阶段回执校验。
- `lib/index.js`：宿主入口——注册 `token2biq` 工具 + `/token2biq/*` Web 路由。
- `lib/client.js`：侧边栏面板 + 输入框旁「IQ」下拉。

真正执行由宿主已有的 `spawn_teammate/team_task_*/send_message/wait_agent` 完成。所以「插件的工作是否正常」要拆成两层看：**编排/校验/持久化（正常）** vs **记账/设置落地（基本不正常）**。

## 二、「记录完全是坏的」——根因与实证

### 实证数据

| 来源 | 数字 | 说明 |
| --- | --- | --- |
| 插件记录 `state.json` | 2 条运行，均 2026-11-03 | `run_mw07bw9s_b`（S3 只读审计）spent=**954**；`run_mw06rvwm_1`（S2 演示）spent=**1650** |
| 面板「累计 token」 | **≈2604** | = Σ 各 run.spent |
| 宿主实时 `liveUsage` | **total 106,777,319**（input 5.26M / output 1.42M / cacheRead 100.09M / 1323 请求 / 8 会话） | 真实发生的用量 |

954 对 106,777,319 —— 差了 5 个数量级。这不是"少记了一点"，而是**两个完全不同口径的数**：

1. **`record()` 把估算当记账**（`lib/service.js` 的 record）。
   当调用方没传 `tokensIn/tokensOut` 时，用 `estTokens(JSON.stringify(args)) = Math.ceil(字符数/4)`，按 60%/40% 拆成 in/out —— 一个完整"审计"回执的 JSON 也就几百字符，于是"整场 S3 审计只花了 954 token"。它标了 `estimated=true`，但**面板从不展示这个标记**，看起来就是真实台账。
2. **面板把"全局实时累计"错当"本插件开销"**（`lib/client.js` 旧 StatsBar）。
   早期版本把 `liveUsage.total`（含本对话自身、含 99.9M 缓存读）直接叫"实时 token / 本插件累计"，严重误导；后来干脆不渲染 liveUsage，只显示 Σrun.spent（假数）。
3. **真实用量从未归集到某个 run**：`noteUsage` 只往全局 `liveUsage` 累加，没有"哪个 run 花了多少"的映射 → 每 run 的 token 只能靠估算，天然是假的。
4. **"这几天的历史对话"里几乎没有记录**：`state.json` 只有 11-03 的两条示例，之后没有任何新 run。原因是记录**只在模型主动调用 `token2biq action=start` 时产生**；日常大家直接用 Agent Teams 干活，没走这个工具，于是面板一直是空的/旧的 —— 这本身就是"记录看起来坏了"的直观来源。

### 已修复
- 新增 `run.real{input,output,cacheRead,cacheWrite,total,requests}`；`noteUsage` 按**当前活动运行**（`start` 建立 `currentRunId`，`finish/pause` 清除）把真实用量归集进去（flush 2s 节流）。
- 面板「运行记录」：有真实用量显示 `N tok`，否则显示 `≈N tok（估算）` + 悬停说明。
- 面板「概览统计」改为 **4 卡：运行数 / 真实 token（实时，来自 llm/stream）/ 回执上报（含估算）/ 一次通过率** + 实时明细行（输入/输出/缓存读/请求）。**两个口径彻底分开，不再互相冒充。**

## 九、补充：「独立评委」为什么之前没做完 / 现在怎么做的

**之前没做完的真实原因**：设置项原写「用官方 agentLoop 直接跑独立评委」。查宿主 API 目录后确认——`agentLoop` 是 agent 工厂/驱动器；所有 `prompt` 类接口只**投递**提示并返回 `{accepted:true}` / `{messageId}`，**没有同步「跑完并返回 verdict」的接口**。插件想自己算出评委结论就必须驱动完整 agent loop + 读会话日志 = 自造运行时（违背设计铁律）；异步起评委又和普通 review 重复、双倍成本。故诚实标「预留」。

**现在的实现（用宿主真正支持的正确形态）**：
- `independentReview=true` 时：`buildRoster` 给 review/judge/redteam 打 `independent` 标记；`record` **硬校验**评委 owner 不能是 generate 执行者（自评拒收）；评委 prompt 追加盲审指令。
- 面板标签改为「独立评委：评审/裁判/红队必须由非执行者的独立代理盲审裁决」。
- 测试 70/70 全绿（新增 3 条），smoke 11/13/5，render 19。
- 若你要「插件自己用指定模型同步跑评委」：宿主无此同步接口，只能异步（≈普通 review 再跑一遍、双倍成本），不建议。
