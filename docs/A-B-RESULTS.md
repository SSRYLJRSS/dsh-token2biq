# A/B 实验结果（pilot）· 官方裸跑 vs 插件严格流水线

日期：2026-11-08 ｜ 目录：`scratch/ab-pilot/` ｜ 原始数据：`results.json`、`runs.json`

## 设计
- 3 个自包含任务（小/中/大），每个都有**隐藏验收测试**（执行方不可见），`node --test` 客观判分。
- **对照臂 C**：单代理裸跑（一份 agent 直接实现，无流程门禁）。
- **处理臂 T**：插件 `pipelineGate=strict`——`spec(acceptance)`→`plan`→`generate`→**独立盲审**→`verify(testsRun)`→`finish`，阶段回执经插件真机 HTTP API 记账，门禁真拦。
- 生成者：两臂同一模型（我），**代码相同**——因此本轮主要隔离「评审+门禁」的收益/开销，而非「团队 vs 单人」的质量差。

## 结果（客观）
| 任务 | 难度 | C 通过 | T 通过 | T 独立盲审 | T 返工 |
|---|---|---|---|---|---|
| t01 clamp | 小 | 3/3 ✅ | 3/3 ✅ | PASS | 0 |
| t02 parseDuration | 中 | 4/4 ✅ | 4/4 ✅ | PASS | 0 |
| t03 topN/groupBy | 大 | 3/3 ✅ | 3/3 ✅ | PASS | 0 |

- 两臂**通过率均 3/3**，断言全过；独立盲审 **3/3 PASS**；**返工 0**。
- 硬门禁证据：t02 的 `review` 回执**因缺 owner（独立评委须独立代理）被拒**——证明 `independentReview` 硬校验在真机生效。

## Token（不可比，仅登记）
- `liveUsage` 是全进程口径：control 跑在 Lead 超大上下文里（≈40.1 万增量），treatment 含 3 个评审子代理（≈51.0 万增量）。**两者不可比，不作为结论**。

## 结论
**在这 3 个自包含任务上，严格流水线没有提升正确率（本来就 100%），只是增加了评审与门禁开销、0 返工。** 这支持之前定的规则：**小任务别开 strict**。要证明“用 token 换质量”真有价值，必须上**生成者会犯错、多文件/高风险**的任务，且让生成者也是真实多代理团队（本轮未触发 autoSpawn）。

## 尚缺（下一轮才能定论）
1. 更难任务集（含隐藏测试的 bug / 多文件 / 架构改动），让生成臂真会出错 → 看盲审能否拦住、返工是否减少。
2. 真·多代理 autoSpawn 端到端（本轮 reviewer 是真实子代理，但插件直接 spawn 队员仍未触发验证）。
3. token 用**隔离等长上下文**两侧同时测（如两侧都用全新子代理），或改用宿主 tokenMeter 的 per-session 差值。

## 最终决策（2026-11-08，方案 B）

**默认 `pipelineGate=off`；仅在「大改/高风险」任务手动开 `strict`。**

理由：本 pilot 小/中/大任务均 100% 通过、盲审无返工，严格流水线纯增开销；其价值只可能在“生成者会犯错”的硬任务上体现，待硬任务集再验。日常保持 off 最省，大改再开。
